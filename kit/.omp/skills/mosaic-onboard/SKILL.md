# /mosaic-onboard — Set personal handoff defaults
Read each named rule once per session; a later step naming a rule you already read means apply it, not reread it.
Read `rule://records` before proceeding.
The only repository edit allowed here is a roster row via a reviewed pull request; never edit flows or preview cards. Personal settings stay outside every checkout.

1. Read `rule://handoff`, `rule://git-flow` and `rule://tracker`; read `.omp/mosaic.json`. Run commands from the link root. Require installed `handoff`; if absent, explain that enabling it is a reviewed `/mosaic-kit` change and stop. Run `bun tools/handoff.ts roster`; structural roster/metadata corruption blocks onboarding, but an absent/incomplete row or missing role coverage may be repaired by a whole-result-valid `roster --set --dry-run` proposal below. Never invent people.
2. Choose self mode (`/mosaic-onboard`) or teammate mode (`/mosaic-onboard teammate <name>`). Confirm the handle and proposed roles with the contributor. Never infer one identity from another or from the runtime account.
## Self mode
3. Confirm each identity with the person: in MCP tracking mode use the named mounted tracker's `list_users`/`get_user` to show candidate id and mention; verify Slack id through the configured mounted server when enabled; use `gh api user` for the GitHub login. Read mounted schemas first. Missing optional identities use `—`; never invent identities, emails or secrets.
4. For an absent/incomplete row, follow **Roster pull request** below, then run the personal-settings steps from that branch. A complete unchanged row needs no PR.
## Teammate mode
5. First establish the contributor separately: use self-mode lookups to confirm their own handle and tracker id/GitHub login for each confirmation surface; an unknown identity blocks that surface, never proves a different person. Then the contributor names the teammate and proposed roles. Draft via verified MCP tracker lookup, or existing verified local replay identity/evidence; verify Slack id through its configured mounted server. The teammate's GitHub login is stated or `—`, never copied from `gh api user`. If their handle or any confirmation identity is the contributor's, route to self mode instead.
6. In tracking mode, create or reuse the contributor-provided item through the tracker rule, retaining its locator and writer token. Re-fetch and enforce writer checks before every write, including on rerun; a foreign/live writer is a conflict, never permission to impersonate it. Post one confirmation comment @mentioning the draft person, with proposed row, roles and what accepting gates means; retain the comment id. Search existing comments before retrying an uncertain post. Notify via handoff's **Slack notifications** when configured. STOP without polling; ask to rerun once they reply.
7. On rerun read all comments completely. Count only the person's explicit confirmation replying to that confirmation id (`parentId`), with author equal to the draft tracker id AND different from the independently confirmed contributor id, `onBehalfOf` null and no sync/relay attribution. Reject contributor-authored confirmation even if it matches the draft identity; route self-onboarding to self mode. Apply corrections; changed roles need a new confirmation and STOP. Preserve writer checks; no onboarding takeover exception exists.
8. Local replay uses the tracker rule's `intent`, `comment` and complete `get`; retain reply author/parent/relay evidence. A receipt is not personal confirmation. With tracking `none`, open the roster PR below as unconfirmed and STOP until a personal GitHub review/comment from the stated teammate login confirms the row and roles. Require that login to differ from the independently confirmed contributor login (case-insensitive); a contributor-authored answer never counts, even when it matches the proposal. Missing identities stop. Read all reviews/comments on rerun, reject bots/relays, and re-ask on changed roles. Never count Slack.
9. After tracker confirmation, follow **Roster pull request**, linking the confirmation item. Teammate mode never writes someone else's user file; direct them to self mode.
## Roster pull request
10. Show `bun tools/handoff.ts roster --set --handle @<handle> [--roles <a,b>] [--tracker-id <id>] [--mention <mention>] [--github <login>] [--slack <id>] [--prefers <text>] --dry-run` with quoted verified identities and proposed roles, personally confirmed as required by the chosen mode; the tracking-none teammate PR must explicitly state confirmation is pending. Supply only changed fields for an update; `—` clears optional fields. Added rows require roles; omitted fields become `—`. Show returned canonical `row` and action before writing.
11. Follow the git-flow light documentation path: branch `roster/<handle-without-@>` from the configured default branch, using the exact dry-run-validated handle (never silently rewrite it). Run the same `roster --set` without `--dry-run` and inspect its result. It validates the whole roster and flows, preserves other bytes and file mode, and atomically replaces the roster only after the complete write succeeds. JSON is `{path,handle,action:added|updated|unchanged,row,written}`; unchanged needs no duplicate commit.
12. Commit only the roster as `roster: add @<handle>` or `roster: update @<handle>`, push and open a PR explaining identities, proposed roles, confirmation evidence and that roles become effective only when the reviewer merges. Do not merge for them. In tracking-none teammate mode, personal confirmation on this PR is required before calling it ready.
## Personal settings (self only)
13. Run `bun tools/handoff.ts user` to show settings and exact path. The committed link-remote key selects one runtime-neutral file under `$XDG_CONFIG_HOME` (else `~/.config`), outside all checkouts.
14. Ask for a committed default flow, `none`, or no default (area matching), and optional per-role acceptors (`bun tools/handoff.ts roster --role <role>`). Never add flows/roles/people through defaults; preferences never widen gate policy.
15. Show the complete replacement and obtain choices; run `bun tools/handoff.ts user --write --me @<handle>` with `--flow <id|none>` only if chosen and `--acceptor <role>=@<handle>` per chosen role, quoting values. For a proposed roster row run from its roster branch. Resolve validation failures with the person; never hand-edit JSON.
16. Run `bun tools/handoff.ts user` and show path, validity and saved settings; require exit 0 with intended content. Defaults involving a proposed row take effect after its reviewer merges; rerun if the reviewer changes the row. Each plan still confirms `flow:`/`acceptors:` with a skip choice.
