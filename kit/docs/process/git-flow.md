Read when: creating a branch, committing, or landing any change.
# Git flow
- Run operations in the targeted repo (`git -C <repo>`); read `rule://plan-home` for repo selection and plan ownership.
- One plan has `task/NNNN-<slug>`, matching its filename, created from up-to-date `{{DEFAULT_BRANCH}}` in every targeted repo{{LANDING_PULL_REQUEST}}, or its declared parent when stacked (`rule://stacked-prs`){{/LANDING_PULL_REQUEST}}; R6 in `rule://plan-home` assigns the artifacts to those branches.
- Commit each completed task in its own repo as `NNNN-T<k>: <summary>`.
- Never commit on {{DEFAULT_BRANCH}}. The `guard-main` hook blocks the targeted repo's commit, including `git -C <repo>`, `cd <repo> &&` anywhere in the command, `bash -c`, `$(…)`, and heredoc scripts; git aliases and scripts on disk are not inspected.
{{LANDING_DIRECT}}
- After sign-off and terminal recording, refresh {{DEFAULT_BRANCH}}, rebase the branch onto its latest tip if it moved (`git rebase {{DEFAULT_BRANCH}} task/NNNN-<slug>`), then `git checkout {{DEFAULT_BRANCH}} && git merge --ff-only task/NNNN-<slug> && git push origin {{DEFAULT_BRANCH}}`; delete the landed branch.
- The same rebase-first and `--ff-only` sequence lands short-lived inline/docs branches; read `rule://plan-triage` for their names and authorization.
- A `--no-ff` merge is allowed only for a genuinely complex case, such as preserving a long-lived diverged branch, with the justification recorded in the plan's Execution log.
{{/LANDING_DIRECT}}
{{LANDING_PULL_REQUEST}}
- `<base>` is the selected repository's declared base, defaulting to `{{DEFAULT_BRANCH}}`. Before every review, squash, push, or landing run `bun tools/stack-base.ts --repo <name> [--plan <path>]` from the link root; read `rule://stacked-prs` and stop on failure or any action other than `none`. Only `none` supplies `base`, `base_ref` (fetched `origin/<base>`), and `base_sha` (its pinned SHA). Use `<base ref>` in history commands and `<base sha>` in review dispatches; never review a movable ref. Bare `<base>` is for PR creation/retargeting. A repository-to-SHA mapping is required for multi-repo review.
- For a stacked PR, pass the current `none` result's `base_sha` to `rule://final-review` as its freshly pinned current PR base SHA for review/replay; keep the previous round's recorded base SHA separately. Final-review owns comments, CI and exact-head readiness.
{{CLOSE_OUT_TWO_COMMIT}}
- For a plan, after sign-off resolve and rebase onto `<base ref>`, retain its base SHA and task subjects, then squash all task-branch commits into ONE code commit before the first push and pull request below: `git reset --soft <base sha> && git commit`, using the plan's subject and listing the task subjects in the body.
- After opening that pull request, retain its locator and make ONE close-out commit containing every terminal documentation change owned by that repo: status, archive move, ledger row with locator, Execution log, and approved registry/gap dispositions. Push it to the same pull request; no follow-up commit records landing.{{MULTI_REPO}} Member-homed plans keep R4's link-repo ledger sync after the member merges. A targeted repo whose pull request owns no terminal documentation keeps only its code commit; open it before the link repo's close-out, which records every targeted repo's locator.{{/MULTI_REPO}}
- Later review/CI code corrections use `git commit --fixup <code commit>` followed by `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <code commit>^`, using the code commit's current parent, not the base SHA saved before a later rebase; amend terminal-record corrections into the close-out commit. Keep the code commit first and any close-out commit last, with no other commits; force-push only with the lease below, then repeat `rule://final-review`'s post-push gate. This plan-only layout does not change inline/docs-branch procedures.
{{/CLOSE_OUT_TWO_COMMIT}}
- After sign-off, resolve the base, rebase onto it (`git rebase <base ref> <branch>`), rerun resolution until `none`, and make the first push (`git push -u origin <branch>`). After rebasing an already-pushed branch, use `git push --force-with-lease origin <branch>`; never force a shared or default branch. Open a pull request into `<base>` non-interactively (`gh pr create --base <base> --head <branch> --title "<title>" --body-file <file>`); the body states what changed and why, plus the evidence. Here `<branch>` is the targeted plan, inline, or docs branch. Obtain its locator before terminal records need it; push subsequent terminal-record changes to the same branch before the merge gate. A stacked child lands only into {{DEFAULT_BRANCH}} after its parent lands (`rule://stacked-prs`).
{{PR_EVIDENCE}}
- For a pull request touching the selected source paths, fill the project's pull request template's `## Evidence` section following [PR evidence](../standards/pr-evidence.md); preserve explicit verification limits.
{{/PR_EVIDENCE}}
- After opening and every push, read `rule://final-review`: its one gate owns every check, every comment (bots included), final review/exemptions and exact-head readiness. Complete it before presenting the PR and again before merge. The human merges and chooses the merge method; delete the branch only after landing and after the successful open-child lookup in `rule://stacked-prs`.
- Short-lived inline/docs branches follow the same rebase-first, push, pull-request, checks, comments, human-merge, and branch-deletion sequence; read `rule://plan-triage` for their names and authorization.
