Read when: branching from an unmerged pull request, working on that child, or when its parent changes or lands.
# Stacked branches and pull requests
- A stacked branch starts at an unmerged parent pull request's head instead of `{{DEFAULT_BRANCH}}`. Stack dependent or overlapping changes; independent changes start at the default branch. The bottom layer targets `{{DEFAULT_BRANCH}}`.
- One worktree holds a whole stack, not a single layer: restacking rewrites higher layers, and Git cannot rebase a branch checked out in another worktree. Independent stacks use separate worktrees.
# Declaring the base
- Each plan has one frontmatter `bases` map: `{ <repo>: { base: <branch>, base-pr: <number or null> } }`. Include exactly every repository carrying the plan branch, including `link-repo` for cross-repo plans; omit untargeted members. A monorepo has only `link-repo`. Use `base: {{DEFAULT_BRANCH_YAML}}` and `base-pr: null` when unstacked; quote branch names as YAML strings. Existing plans without `bases` mean the default branch; do not add scalar `base`/`base-pr` fields.
- Resolve the one plan home under `rule://plan-home`, not copies in each member. Parent PR numbers are repository-local; a parent in a different repository is a dependency, not a Git stack. Each repository may declare a different parent.
- A no-plan branch records `Base: <parent branch> #<number> for <own branch>` in its commit message when cut from `origin/<parent branch>`. Keep it through amend/squash; resolution reads the newest trailer owned by that exact branch, even beneath trailer-free fixups. Inherited-only trailers stop; refs and PR targets cannot replace the declaration.
# Resolving and acting
Run `bun tools/stack-base.ts --repo <name> [--plan <path>]` from the link root before every review, squash, push, or landing. The path is link-root-relative, including a member-home prefix. It fetches and reads only, scopes Git and GitHub to the selected configured repository, and never executes printed commands. Its ordered output is `branch`, `kind`, `declared`, `parent`, `base`, `base_ref`, `base_sha`, `own_pr`, `old_tip`, `pending`, `action`, `command` as `key=value` lines.
- Exit 0 means evaluated, not ready. Only `action=none` supplies the base tokens for the guarded step (`rule://git-flow`). Exit 1 stops; exit 2 cannot evaluate; both print one stderr reason and no stdout. Never continue on either failure.
- `action=restack`: run the printed command, rerun until `none`, then push with `git push --force-with-lease origin <branch>`. Apply task review under `rule://review-loop` to any changed own patch (`git range-diff`); use `rule://final-review` for replay, comments, CI and exact-head readiness. Git-flow supplies the resolver's freshly pinned `base_sha` to that replay.
- `action=land`: perform pending work in order: history, declaration, retarget. Run `command` when nonempty. For `declaration`, change only the selected repository's active `bases` entry to `{ base: {{DEFAULT_BRANCH_YAML}}, base-pr: null }`; never rewrite archived plans. For no-plan branches replace the newest commit's trailer (`git -c trailer.Base.ifExists=replace commit --amend --no-edit --trailer 'Base: {{DEFAULT_BRANCH}} for <own branch>'`), never a plain fixup whose message autosquash drops. Commit active-plan changes via git-flow's configured correction path. For `retarget`, run `gh pr edit <own_pr> --repo <configured remote> --base {{DEFAULT_BRANCH}}` only if still needed. Push history/declaration changes with `--force-with-lease`, re-read state, and rerun until `none`; apply task review and `rule://final-review` as above.
- Plan-on-plan history uses guarded parent subjects; other stacks use the remote fork point. Missing/unsafe boundaries, child commits below a proposed cut, merges during history judgment, foreign plan subjects, failed/ambiguous PR reads, malformed declarations, or moving fetched refs stop resolution. A pruned parent's last PR head is not an automatic safe cut: a conditional ref-restoration stop requires proving the parent was not force-pushed since the last restack before restoring and rerunning.
- Own and parent PR heads must identify this configured repository, including owner; fork heads and unknown identities stop. Before printing history commands, validate excluded and replayed plan history, permitting parent-plan subjects and proven inherited parent history but rejecting foreign subjects. Merged-parent fork points use the existing local tracking ref/reflog; the resolver does not refresh that parent or replace its boundary with the recorded PR head.
- Known limit: a merged parent's stale local tracking ref can make landing replay inherited commits, surfacing as a rebase conflict. Fetch its final head with `git fetch origin refs/pull/<n>/head`, verify that it is the inherited parent tip, restore the parent tracking ref as below when needed, then rerun. The same fetch can recover a missing merged-head object after reason 9; fetching an object alone does not approve a boundary. For reason 10 on inherited history in a fresh clone after a grandparent rewrite, recover and verify the old parent tip this child inherited, then restore its tracking ref with `git update-ref refs/remotes/origin/<parent> <old-parent-tip>` and rerun. Use the explicit verification/restore procedure from the pruned-parent recovery above; never invent an old tip.
- Known limit: origin is accepted when either the stored or the `insteadOf`-expanded form of its first fetch URL identifies the configured repository (HTTPS, SSH and `insteadOf` aliases of it all match). If the stored form matches but an `insteadOf` rule rewrites it to a different repository, that isn't detected, and the resolver would read that repository's base. Don't rewrite this host's URLs to other repositories in clones used for stacking.
- `none` with an open parent permits review/push, not landing. Merge a child only into `{{DEFAULT_BRANCH}}`, after its parent landed and resolution is `none`; never merge it into the parent's branch.
# When the parent lands
- GitHub may automatically delete the parent and retarget the child, or neither. A child targeting the default branch may still carry inherited parent commits; keep its recorded parent until the transition above finishes.
- Delete a landed parent manually only if GitHub did not, and only after `gh pr list --repo <configured remote> --base <parent branch> --state open` succeeds and lists no children. Failed lookup keeps the branch.
- Preserve both parent and child ledger rows on conflict, never one side's entire table. When tracking is enabled, record the existing parent's item as a dependency; do not create an item for an untracked parent.
