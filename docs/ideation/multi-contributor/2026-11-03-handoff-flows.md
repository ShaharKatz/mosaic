# Handoff flows: a human-to-human acceptance gate before merge

Scope: one slice of the [multi-contributor design](2026-10-31-jobs-roles-surfaces.md). A change that is reviewed, verified and CI-green is handed to a named person outside engineering (a designer, a product manager, QA) who accepts it on the surfaces they use; then the contributor merges. Everything else in that design stays deferred.

Facts about mosaic cite `kit/` on this branch (`4deeffe` plus the Mermaid commits). Linear facts were read today from the CTM team and [linear.app/docs/github](https://linear.app/docs/github). mb-platform facts come from `~/Projects/mb-platform-gw3/.omp/mosaic.json` and its CI workflows.

## Summary

- **A handoff is a landing precondition, not a plan status.** It sits where final review already sits in pull-request mode: after reviewers are clean, verification is recorded, comments are ruled and CI is green on the exact head, and before the human merges. The plan is already `done` and archived by then (`mosaic-execute` step 10), so no status, ledger column or lint enum changes.
- **A flow is a named list of gates; phase 1 has one gate kind, `acceptance`.** A gate names a role from a roster, the surfaces where that role may accept, the artifacts the packet carries (pull request, preview), and the tracker event it maps to. Flows are selected per plan: by area match or by the contributor's default, confirmed in the approval brief, recorded as `flow:` in the plan's frontmatter.
- **Definitions are committed; personal defaults are not.** What a gate is, which roles may accept it and what it writes to the tracker is shared process and lives in the repo, reviewed and validated offline. So do each person's acceptance preferences, because other people's sessions act on them. Who I am, which flow I default to and whom I usually hand to is personal and lives in a user file outside every checkout, generated by a `/mosaic-onboard` step. The plan, not the user file, is the record of what was chosen.
- **Acceptance is evidence, not a state.** An acceptance counts only as a reply by a roster person in the thread of mosaic's handoff comment, or a pull-request review approval by that person's code-host account on the handed-off head. A tracker state alone never counts (today's rule, `tracker.md:100`). A code change after acceptance makes it stale; a docs-only change does not, using final review's replay check.
- **Surfaces are named by operation, with a Linear map.** The gate needs four tracker operations (`read-item`, `set-state`, `add-comment`, `list-comments`) and one code-host read (`list-reviews`), plus two optional code-host writes mosaic already performs (`edit-pr-body`, `request-review`); §6 lists them. Today's `mcp` mode is written in Linear's tool names; this is the first rule written against operations, so a Jira or GitHub Issues binding later only adds a map. Without a tracker, the gate still works through a GitHub review request.
- **Preview is a project surface.** A card says how a preview for a head is produced, how to obtain its URL and how to verify which commit it serves. Production may be a CI pipe mosaic observes, a project-owned skill or command mosaic runs under the flow's approval, or a URL the human supplies; the kit ships no deployer. mb-platform's planned secretless-portal skill is the second kind.
- **Feedback after `done` is a repair round, not a reopened plan.** In pull-request mode `done` means signed off and close-out written; the pull request is what is still open, and the kit already repairs code and amends the close-out commit after `done` for final-review and human comments. A returned handoff uses that path, classified as defect, amendment or deferral (§5.3).
- **Seven rulings** (§9), one blocking: the writer-token rule needs an amendment so the contributor's next session can resume the item.

## 1. The job

**When** a change is ready to merge, **the contributor** needs a named person who did not write it to accept it on the surfaces that person uses, with the exact thing under review pinned, **so that** the merge carries that person's acceptance and nobody chases status in chat.

This is distinct from J9 in the main design (handing a plan to another engineer to continue). Here ownership does not move: the contributor stays owner, waits, and merges.

The mb-platform instance: a frontend change goes to the designer or the product manager before merge. The Linear item moves to a `QA` state placed after `In Review`. The acceptor looks at the pull request and, when one exists, at a deployed preview of the branch. On acceptance, the contributor merges.

## 3. Flows and gates

### 3.1 Vocabulary

| Term | Meaning |
|---|---|
| Flow | A named, ordered list of gates a plan passes between readiness and merge. `none` is a valid flow |
| Gate | One acceptance by one role on declared surfaces with declared artifacts |
| Role | A roster role: `designer`, `product`, `qa`, or any name the project declares |
| Acceptor | The roster person who holds the gate's role for this plan; resolved at request time, not at plan time |
| Packet | What the acceptor is given: plain-language summary, what to check, pull-request locator, preview link, evidence path, head SHA |
| Readiness | Final review's exact-head result in pull-request mode (`final-review.md:41-42`) |

### 3.2 Shape

Runtime metadata (`.omp/mosaic.json`), as built: one optional `handoff` key, like `review` or `standards`, written by the installer from the install manifest. No metadata schema bump.

```json
"handoff": {
  "flows": [
    { "id": "design-acceptance",
      "areas": ["services/frontend/**"],
      "gates": [ { "role": "designer", "surfaces": ["tracker-reply", "pr-review"], "artifacts": ["pr", "preview"], "state": "QA" } ] },
    { "id": "product-acceptance",
      "gates": [ { "role": "product", "surfaces": ["tracker-reply"], "artifacts": ["pr"] } ] }
  ],
  "preview": "docs/surfaces/preview.md",
  "requestReview": false
}
```

- `areas` is the optional team-default selector; absent means manual selection only. `artifacts` defaults to `["pr"]` and always includes it.
- `state` maps the handoff event to a team-native state; MCP tracking only (the local replay tracker uses the event name).
- `preview` names the project-owned preview card (§6.3). `requestReview: false` records the owner's attestation that a tracker automation reacts to GitHub review requests (§6.1), so mosaic notifies through the tracker mention only.
- The roster path is fixed: `docs/surfaces/people.md`. Every grammar (metadata, roster, preview card, user file, plan frontmatter, Execution-log lines) lives in one module, `tools/constants/handoff.ts`, shared by the installer, doctor, lint and `tools/handoff.ts`.

Rules on the shape:
- A gate has exactly one role. Two acceptors are two gates, run in order. No quorum, no delegation, no timeout: silence is not approval (`mosaic-core.md:9`).
- **A gate is policy; a person's preference is not.** `surfaces` and `artifacts` are the sets that *count*. Which of them a given acceptor wants to be asked on, and what they want in the packet, is that person's preference in their roster row (§3.4); the request honors it, and an acceptance on any allowed surface still counts.
- `surfaces` is a subset of what the installed bindings can provide: `tracker-reply` needs a tracker (`mcp`, or `local` replay) whose comments expose author, thread and relay attribution; `pr-review` needs pull-request mode on GitHub. The installer and doctor reject a surface the install cannot serve.
- `state` must name a state the team has (`list_issue_statuses` at install; the installer and doctor check only that it is a nonempty single-line string, as they do for `queue`).
- A flow's `areas` selector is matched against the plan's `areas:` globs. It sets the team default; a personal default (§4) overrides it; the approval brief always confirms. No gate is mandatory in phase 1: "skip handoff" is always available at approval and recorded with a reason. A team that wants enforcement gets it from the host (`CODEOWNERS` plus required reviews, §6.2) or asks for a `required: true` flag as a later ruling.

### 3.3 The plan-time question

In `/mosaic-plan` Phase 1 step 4, when frontmatter is filled, the orchestrator runs `bun tools/handoff.ts resolve --plan <path>`, which applies this precedence: the plan's own `flow:` once set, else the contributor's default from the user file (§4), else a single `areas` match, else `none`; several matches leave the choice to the approval brief. The approval brief (Phase 3) states it in plain words:

> Before merge, this change will be handed to the designer for acceptance on the Linear item and the pull request. Say "skip handoff" to land after reviewers and CI only.

The human's answer is recorded as frontmatter before `draft → approved`:

```yaml
flow: design-acceptance         # or: none — <reason>
```

The gate's *role* is part of what the human approved. The *person* is resolved when the request is made (§5.1). Changing the flow after approval is a mid-flight amendment under `mosaic-execute` step 14: human approval recorded in the Execution log.

### 3.4 Role versus person

Two designers with the same role may work differently: one answers in Linear and wants the preview, the other answers on the pull request and wants the diff. Two engineers with the same role may want different defaults: one always hands frontend work to design, one never does. The model separates the two kinds of difference:

| Difference | Belongs to | Lives in | Read by |
|---|---|---|---|
| What counts as acceptance for a gate | The gate (policy) | `flows[]` | Every session verifying an acceptance |
| Where a given acceptor wants to be asked, what they want in the packet, how they want to be notified | The acceptor (preference) | Their roster row: `prefers: { surface: tracker-reply, artifacts: [preview, pr], notify: mention }` | Other people's sessions when they request acceptance, which is why it is committed, not in the acceptor's own user file |
| Which flow I use by default, whom I hand to | The contributor (preference) | Their user file | Only their own sessions |

A preference never widens policy: a roster row cannot name a surface the gate does not allow, and doctor checks that. The request is built from the acceptor's row within the gate's sets; a missing row preference means "every allowed surface, every available artifact".

## 4. Where definitions live: repo versus person

The main design's first principle applies: one authority per fact, and the plan is the record.

| Fact | Lives in | Why |
|---|---|---|
| Flow definitions (gates, roles, surfaces, tracker state) | `.omp/mosaic.json` `flows`, committed; Registry class | They decide what an acceptor sees and what blocks a merge. Teammates must see them; doctor validates them offline; a change is a reviewed commit |
| Roster (handle, roles, Linear user id and display name, GitHub login, acceptance preferences) | `docs/surfaces/people.md`, committed; Registry class | An acceptance is a record; it must point at a person the repo knows, and other people's sessions act on that person's preferences. No emails, no secrets |
| Preview surface (how a preview is produced, how to obtain the URL for a head, how to verify the served commit, auth, lifetime, teardown) | `docs/surfaces/preview-<id>.md`, committed | Project capability, not a personal one |
| Who I am; my function; my default flow; my usual acceptor | `~/.config/mosaic/<project-key>/user.json`, never committed | Personal, changes often, differs per contributor; no reason for review; nobody else's session reads it |
| Which flow this plan uses; who accepted; on what head | The plan: `flow:` frontmatter and Execution log lines | The record |

**Why the user file lives in the home directory, not gitignored in the checkout.** mb-platform has fourteen checkouts of one remote. `<project-key>` is the link repository's remote from committed metadata (`repositories[link-repo].remote`, present in pull-request mode) normalized to `host/owner/repo` (`github.com/brandlight-ai/mb-platform`), so every worktree derives the same key without running git. The path is `$XDG_CONFIG_HOME` (else `~/.config`)`/mosaic/<project-key>/user.json`, runtime-neutral so both the omp and Claude ports read one file.

**The user file is structured and validated, never a free-form note:**

```json
{ "schema": 1, "project": "github.com/brandlight-ai/mb-platform",
  "me": "@shahar",
  "defaults": { "flow": "design-acceptance", "acceptors": { "designer": "@dana" } } }
```

- `me` and every `defaults.acceptors` handle must resolve in the committed roster, and an acceptor must hold the role it is named for. `defaults.flow` must name a committed flow or `none`. The contributor's function is their roster roles, not a second copy here.
- `bun tools/handoff.ts user` validates the file, and every `resolve` re-validates it; absence is fine (committed defaults apply, and the approval brief asks). Doctor does not read it: doctor stays repo-scoped and gives the same answer on every machine and in CI.
- A personal flow that nobody else uses is still a committed flow definition. Keeping definitions out of the repo would hide an acceptor's expectations from the team and from doctor; adding one is a few reviewed lines.

**`/mosaic-onboard` generates the user file.** A new skill, run by each contributor once per project: list the roster (`bun tools/handoff.ts roster`); ask who you are (match a roster handle; when absent, propose a roster row as a normal reviewed docs change), your default flow and per-role acceptors; write the file with `bun tools/handoff.ts user --write …`, which validates before writing. It writes nothing into the repo. `/mosaic-kit` is not the vehicle: it branches to `kit/<slug>` for kit changes.

## 5. The gate, step by step

Phase 1 covers pull-request mode (mb-platform's). Direct mode is a ruling (§9 R6).

### 5.1 Request

After `mosaic-execute` step 12 reaches a stable exact-head readiness and before the merge:

1. **Resolve the acceptor:** the plan's `acceptor:` if set, else the user file's `defaults.acceptor` if that person holds the gate's role, else ask the human in-session. The acceptor must be on the roster with the role. Read their roster preferences (§3.4) to choose, within the gate's sets, which surfaces to post on and which artifacts to include.
2. **Produce or obtain the preview** when the gate's artifacts include `preview` and a preview card exists, by the card's `produce` mode (§6.3): observe the CI pipe's URL for `<head sha>`; or run the project-owned skill or command, which the approved `flow:` authorizes for this plan; or ask the human for the URL. Verify the served commit the way the card says; a preview that serves another commit, or cannot be verified, is carried as such or omitted, and the packet says so.
3. **Pin the artifacts:** `<head sha>`, `pr://<n>`, the evidence packet path, and the preview link with its served commit.
4. **Write the packet** under `rule://human-gates`: audience is the acceptor; first sentence says what changed and what they are asked to accept; "what to check" is derived from the plan's acceptance criteria in plain words; at most 40 lines; the head SHA appears once, in parentheses, to locate the thing.
5. **Journal first.** Append to the Execution log:
   `- handoff R<n> <role>: REQUESTED @<handle> <ISO> head <sha> pr://<n> preview <url|none>`
   then commit. In two-commit close-out this amends the close-out commit and force-pushes with lease, as final-review evidence already does; replay then confirms a docs-only delta.
6. **Post**, by binding and by the acceptor's preferred surfaces:
   - Tracker (`mcp`): re-fetch the item (writer check), `set-state` to the gate's mapped state if H-pipes assigns that field to mosaic, `add-comment` with the packet, the `@` mention of the acceptor and today's marker scheme. Search for the marker before any retry. Never touch assignee, priority or labels.
   - Code host: `edit-pr-body` to add `[Branch Preview](<url>)` when a preview exists (Linear surfaces it); `request-review` for the acceptor when `pr-review` is among their surfaces and no attested pipe turns a review request into a tracker state change (§6.2).
   - No tracker (`none`) or replay (`local`): the request is the Execution log line, the pull-request body and the review request. In `local`, the outbox gets the `handoff` event.
7. **Stop** with a brief to the contributor: whom it went to, where, what the acceptor will see, and that the next step is to run `/mosaic-execute <plan>` again once the acceptor has answered. The session does not poll and does not wait on a timer.

### 5.2 Resume and verify

A later invocation of `/mosaic-execute` on a plan whose last Execution-log handoff line is `REQUESTED`:

1. **Writer:** re-read the managed block. The last event is `handoff` and the token belongs to a session that is gone. With the human's in-session confirmation, record the next generation for this session (§9 R1). A token that belongs to a *live* session is still `WRITER-CONFLICT`.
2. **Read every acceptance surface completely**, as final review reads comments:
   - Tracker: `list-comments` to the last page; select replies whose `parentId` is the latest handoff comment, whose author's user id matches the acceptor's roster entry, with `onBehalfOf` null, and that did not arrive through a chat or email sync.
   - Code host: `gh api pulls/<n>/reviews --paginate`; select `APPROVED` reviews by the acceptor's GitHub login that is a roster person, not an app or bot, with `commit_id` recorded.
3. **Bind to the head.** An acceptance covers the head it was given: the SHA in the handoff comment's body, or the review's `commit_id`. Run final review's replay check from that SHA to the current head; an empty own-code delta keeps the acceptance, a code delta makes it stale.
4. **Decide:**
   - **ACCEPTED:** log `- handoff R<n> <role>: ACCEPTED @<handle> <ISO> <tracker-reply|pr-review>/<id> head <sha>`, re-read the record, and proceed to the existing merge gate: the human merges. After landing, the `done` event and landing proof follow today's rule; on Linear the merge automation has already moved the item to Done.
   - **RETURNED with feedback:** §5.3.
   - **Stale:** an acceptance of an older head after a code change is reported, not used; request `R<n+1>` with the own-code delta named in the packet.
   - **Nothing yet:** report that, with the request's age, and stop. Silence is not acceptance.
   - **Wrong person:** a reply by someone not holding the role, an on-behalf-of or relayed comment, or a bot review is reported as seen and not counted.
5. **Still holds before merge:** immediately before telling the human to merge, re-read the accepting comment or review (present, body unchanged) and re-run the head check. A change is a finding that holds the merge.

### 5.3 Returned after `done`

The plan says `done`, is archived, and its close-out commit is on the open pull request. None of that changes on a return, and none of it blocks repair:

- **`done` means signed off, not landed.** The ledger's Landed cell and the landing proof say landed (`git-flow.md:29`). In pull-request mode the kit already writes to the archived plan's Execution log after `done`: final-review verdicts and comment dispositions go there (`final-review.md:33`), and "terminal-record corrections are amended into the close-out commit" (`git-flow.md:21`). The Archive-class freeze (`records.md`) applies once the pull request has landed. A return extends an existing window; it does not open a new one.
- **The repair machinery exists.** A human pull-request comment or a final-review `REVISE` after `done` is repaired by "owning executor repairs, required task reviewers approve the repair delta, then the final engine sees any own-code delta", with affected verification and acceptance scenarios re-run (`final-review.md:30`); code corrections are fixups autosquashed into the code commit (`git-flow.md:21`). A returned handoff takes exactly that path.

What is new is the classification, because the acceptor is a second human whose feedback may or may not be what the first human approved:

| Kind | Test | Route | Sign-off |
|---|---|---|---|
| **Defect** | The change does not meet an acceptance criterion of the plan | Substantive finding; review-loop repair; re-verify; final-review replay; new request `R<n+1>` | None needed: the earlier sign-off covers within-scope corrections (`mosaic-execute` step 9) |
| **Amendment** | Criteria are met, but the acceptor wants it different, and the change stays within the approved scope and `files:` | The contributor decides in-session: accept as an amendment, recorded in the Execution log under step 14, then repaired as above; or contest it back to the acceptor with a reason in the thread | The amendment approval is the re-sign-off; the brief names the new behavior |
| **Deferral** | Pre-existing bug, unrelated request, or a change outside the approved scope | Recorded with reproducer and evidence through the installed tracking mode as a new item, light path or draft plan (`mosaic-execute` step 7's defect route); named in the next request so the acceptor can accept with the deferral or hold | None; the acceptor's acceptance of the deferral is in their reply |

Mechanics across all three:
- **Log, then repair.** `- handoff R<n> <role>: RETURNED @<handle> <ISO> <surface>/<id> (<k> findings)` followed by one line per finding in review-loop format with its disposition (`fixed`, `amended: …`, `deferred: <locator>`, `contested: reason`). `bun tools/handoff.ts status` validates the count, as lint does for `REVISE` on active plans.
- **Tracker state during repair:** re-emit the existing `executing` event so the item shows as in progress again; the next request re-emits `handoff` → `QA`. No new state mapping.
- **Head moves, acceptance restarts.** Every repair makes the earlier thread stale by construction; `R<n+1>` opens a new thread whose packet names the own-code delta since `R<n>`, so the acceptor re-checks the delta, not the whole change.
- **Two returned rounds, then the human decides**, mirroring final review's limit. The decision is one of: another round, override with a named author, or abandonment.
- **Abandonment** is the third outcome when the acceptor rejects the approach rather than the details: `mosaic-execute` step 14 applies, the pull request is closed unmerged, the plan is marked `abandoned` with the reason, the ledger row and links are repointed, and the tracker gets `abandoned`. The code stays reachable in the closed pull request.

### 5.4 Withdraw and override

- The contributor may withdraw a request (`WITHDRAWN <reason>`), for example to land an urgent fix; this is a mid-flight amendment of the approved flow and needs the human's recorded decision in the Execution log, exactly as skipping a plan's gate would.
- Only the acceptor's later acceptance or a recorded human override clears a `RETURNED`; the override names its author, as review waivers do (`final-review.md:9`).

### 5.5 Invariants added in review (2026-11-04)

Three independent reviews of the build (two model families) found ways an acceptance could be spoofed or skipped. The built kit enforces:

- **Explicit flow.** Every plan past draft records `flow:` exactly once; `tools/handoff.ts status` refuses a plan without one or with a duplicate, and lint flags both, so deleting or shadowing the line cannot clear a gate. Switching the module on backfills `flow: none — predates handoff` on in-flight plans.
- **Not the contributor.** The acceptor is someone other than the contributor: `resolve` rejects the user file's `me` as a plan or default acceptor, picks an only holder of the role only when the user file says who the contributor is, and otherwise leaves the acceptor to the human; without a user file the rule requires confirming the contributor's handle in-session. The approval brief names the acceptor either way, and the rule forbids counting the contributor's own review.
- **The log proves what it can.** `status` checks that a requested acceptor is a roster holder of the role, that an answer cites a surface the gate allows and the acceptor has an identity on, and that a tracker reply binds to the requested head. One tracker id or GitHub login belongs to one roster row.
- **Answers belong to the round.** A pull-request review counts only when submitted after the round's request and still in its latest state. A new round may supersede an open one (stale head, another acceptor); answers then cite only the new round.

## 6. Surfaces by operation

### 6.1 Tracker

The gate uses four operations. The Linear column is today's binding; another tracker adds a column, not a rewrite.

| Operation | Used for | Linear (`mcp` mode today) | Needed guarantee |
|---|---|---|---|
| `read-item` | Writer check before every write; current state | `get_issue` | Managed block and state readable |
| `set-state` | `handoff → QA`; `executing` again on a return | `save_issue` with `id` and the mapped `state`, after a fresh read | A team-native state name resolved at install |
| `add-comment` | The request packet, as a new thread with the acceptor mentioned | `save_comment` with `issueId`, `@displayName`, marker | Idempotence by marker search |
| `list-comments` | Reading the acceptance: replies in the request's thread, who wrote them, for whom | `list_comments` paginated; `author`, `onBehalfOf`, `parentId` | Distinguishes people from agents and relayed messages; without this the surface cannot carry acceptance |

Pipes to respect on Linear (owner-attested at install, H-pipes): pull request opened → In Progress; review requested → In Review; merged → Done. Two consequences:
- The "ready for merge" automation must not target the gate's state, or every mergeable pull request, including `flow: none` plans, would enter `QA` before mosaic's own gate.
- A GitHub review request fires "review requested → In Review" and would move the item out of `QA` asynchronously. When that pipe is attested, mosaic does not call `request-review`; the tracker mention is the notification, and the acceptor can still approve on GitHub without a formal request.

### 6.2 Code host

One read and two writes, all through `gh`, all already used by the kit:

| Operation | Used for | GitHub today | Note |
|---|---|---|---|
| `list-reviews` | Reading an acceptance given as a review: login, `state`, `commit_id` | `gh api repos/<o>/<r>/pulls/<n>/reviews --paginate` | Final review reads the same endpoint (`final-review.md:39`); the login must be a roster person, not an app or bot |
| `edit-pr-body` | Adding the `[Branch Preview](<url>)` line | `gh pr edit --body-file` | Mosaic owns the body already (`git-flow.md:23`); Linear turns the link into a preview shortcut |
| `request-review` | Notifying an acceptor who works in GitHub | `gh pr edit --add-reviewer <login>` | Skipped when the review-requested pipe is attested (§6.1) |

`pr-review` is GitHub's review approval on the exact head. Where acceptors work in GitHub, the owner may also make the host enforce the gate (`CODEOWNERS` for `services/frontend/**` plus required reviews); mosaic then observes an acceptance the host would have required anyway.

### 6.3 Preview

A preview is whatever lets the acceptor use the change before it lands. Its card, `docs/surfaces/preview-<id>.md`, follows the main design's card sections and adds a `produce` mode:

| `produce` | How the URL for a head appears | Who acts | Authorization |
|---|---|---|---|
| `pipe` | CI deploys every pull-request head; the URL is in a deployment, check run or bot comment (Vercel, Netlify) | Nobody in-session; mosaic observes | None beyond the pipe's attestation |
| `skill` or `command` | A project-owned skill or `rule://stack` command builds and serves the head somewhere; mb-platform's planned secretless portal is this kind | The orchestrator runs it at request time (§5.1 step 2), or dispatches the project's agent for it | The approved `flow:` whose gate carries `preview` authorizes the run for that plan; the card names cost, lifetime and teardown, and the human may be asked per run if the card says so |
| `manual` | The human supplies a URL | The human | None |

In every mode the card also says: how to verify the served commit (a version endpoint, a deployment's `sha` field, a build tag; without it the preview is carried as "unverified: may not serve the handed-off head"); authentication and whether the URL may be written to the tracker (classification; a "secretless" portal still needs this stated); lifetime and teardown (after acceptance, after merge, or on a timer, and who does it).

What stays fixed: the kit ships no deployer and no portal; a preview never touches a shared or production environment; the served commit is verified or declared unverified; the run is authorized by the plan's approved flow, not by the session's judgment. This narrows the main design's "no deploying" non-goal to shared environments rather than withdrawing it. The frontend reviewer's "safe preview procedure" (`frontend-review/SKILL.md:28-29`) is the same idea with a per-review gate; the card can be its single home.

mb-platform today has no `pipe` preview. Until the portal skill lands, the first handoffs carry the pull request and the evidence packet; the card is written when the skill exists, and the gate's `artifacts` then include `preview`.

### 6.4 Chat

Not in phase 1. The tracker mention and the GitHub review request are the notifications; both are existing pipes. A Slack notification is the main design's phase 3.

## 7. Several functions, several people

- **A function's flow is a flow definition.** Frontend changes go to a designer (`design-acceptance`); billing changes go to product (`product-acceptance`); a data pipeline has `none`. Selection by personal default or `areas:` match; the approval brief always says which applies.
- **Two people in one role are two roster rows**, not two gates: the gate's sets are the policy, each row's `prefers` says how that person wants to be asked (§3.4). The role is resolved to one person per request.
- **Two acceptors are two gates in order**, each with its own request, thread and log line. The second request is made only after the first acceptance holds.
- **A product manager as contributor** has the same path: their user file names `product` as their function and, say, `design-acceptance` as default; nothing in the gate depends on the contributor's function except the default.
- **Limits kept on purpose:** no parallel gates, no "any one of these people", no delegation, no lazy consensus, no reminders. Each is a later ruling with its own scenario.

## 10. Relation to the main design

This slice pulls forward, in a minimal form, four pieces of [the multi-contributor design](2026-10-31-jobs-roles-surfaces.md): the roster and evidence contract (§8: a human action by a roster person, bound to the exact artifact, recorded and re-checked at the gate), abstract tracker operations with a per-tool map (§4.1), one surface card for previews (§6.4), and attested pipes (§9.6). It does not take the payload hash, the event journal, observation envelopes, reconciliation, or any chat or knowledge surface; the plan's Execution log and today's comment markers carry the records. If those later land, the handoff lines become journal entries and the acceptance binds to the payload hash in addition to the head.
